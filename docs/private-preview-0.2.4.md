## 이번 변경의 핵심

0.2.4는 새로운 STT·번역 기능 릴리스가 아니라 **삭제 lifecycle의 데이터 일관성을 보강한 후보**입니다.

- 회의를 삭제하면 그 회의에서 파생된 업무 상태와, 해당 상태를 참조하는 연속성 제안·검토·거절·
  모호성 기록·적용 의도를 타입이 있는 ID로 찾아 함께 정리합니다.
- 프로젝트를 삭제하면 그 프로젝트 범위의 연속성 기록을 함께 정리하되 다른 프로젝트의 기록은
  건드리지 않습니다.
- 두 저장소 사이에서 삭제가 중단될 수 있으므로 삭제 의도를 먼저 기록하고, 다음 실행에서 완료되지
  않은 정리를 복구합니다.
- 삭제와 복구가 제안을 자동 승인하거나 업무 상태를 임의로 적용하지는 않습니다.

## 외부 전송 범위와 비용

앱을 열거나 Continuity Brief를 보는 것만으로 모델을 호출하지 않습니다. 사용자가 전사·추출·재시도를
실행할 때만 본인의 OpenAI API 키로 요청하며, 비용은 그 키의 계정에 발생합니다.

- 전사 요청에는 사용자가 선택하거나 녹음한 회의 오디오가 전송됩니다.
- 추출 요청에는 회의 제목·전사 내용과 판단에 필요한 최소 승인 상태 문구가 전송됩니다.
- 프로젝트·회의·참석자 UUID, 로컬 프로필, 기존 근거 인용문은 보내지 않습니다.
- 요청은 `store: false`로 전송합니다.
- API 키는 앱에 포함되지 않으며 이 Mac의 Keychain에 저장됩니다.

429 또는 5xx 응답에는 한 번의 추출당 최대 2회 재시도하므로 HTTP 요청은 최대 3회가 될 수 있습니다.
타임아웃과 네트워크 실패는 자동 재시도하지 않습니다.

## 삭제와 복구

저장된 회의·프로젝트 기록과 연속성 사이드카를 먼저 정리하고, 오디오 파일은 마지막에 일반 파일
삭제로 제거합니다. 이 순서는 저장된 회의가 이미 사라진 오디오를 가리키는 상황을 피하기 위한
fail-closed 선택입니다.

다만 **두 저장소 정리가 끝난 뒤 오디오 파일 삭제 전에 앱이 종료되거나 프로세스가 중단되면**, 다음
실행에서 그 오디오 경로를 다시 찾을 기록이 없어 `Audio/`에 고아 파일이 남을 수 있습니다. 따라서
이 빌드는 “프로젝트나 회의를 삭제하면 모든 파일이 어떤 중단 상황에서도 반드시 제거된다”고
보장하지 않습니다.

완전 삭제가 필요하면 앱을 종료한 뒤 다음 폴더를 직접 확인하거나 전체 폴더를 삭제하세요.

```text
~/Library/Application Support/com.haena.HAENA/
```

Keychain의 API 키는 별도입니다. *키체인 접근* 앱에서 `com.haena.HAENA`를 검색해 지울 수 있습니다.

## 검증 상태

- 삭제 lifecycle 관련 focused test suites: **149/149 통과**
- 패키지 버전 `0.2.4 (8)`, universal 아키텍처, ad-hoc 서명, SHA-256 재확인
- 패키지에 키·실제 회의·사용자 데이터·개발용 fixture가 포함되지 않는지 확인

아직 남은 확인은 **패키징된 앱으로 실제 핵심 루프를 짧게 사용해보는 것**입니다. 저장 → 추출 → 사용자
검토·승인 → 다음 Continuity Brief → 종료·재실행을 확인하고, 실패 후 재시도와 승인 전 자동 적용이
없음을 함께 봅니다. 이 확인 전에는 Public-ready로 간주하지 않습니다.

## 알려진 제한

- **서명·공증 없음.** 첫 실행에 우클릭 → 열기가 필요합니다.
- **자동 업데이트 없음.** 새 빌드는 직접 받아 교체해야 합니다.
- 삭제가 오디오 unlink 직전에 중단되면 위에 설명한 고아 파일이 남을 수 있습니다.
- 회의록을 수정해 다시 분석하거나, 이미 결과가 나온 회의를 다시 분석하는 기능은 없습니다.
- 오디오 전사 품질은 잡음·다화자·전체 언어 범위에서 정량 검증되지 않았습니다.
- 혼합 언어 자동 감지와 회의 후 번역은 구현되지 않았습니다.
- Calendar 연동, 다중 사용자·팀·동기화는 없습니다.
- 다음 회의 준비는 사용자가 직접 엽니다. 자동 적용과 일괄 승인은 없습니다.
